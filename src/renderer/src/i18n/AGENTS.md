# Agent 中英文文案与翻译指引

## 产品文风

Treefold 保留英文产品名和核心概念，中文负责让用户理解操作、状态、描述和后果。中文界面应自然、简洁，不追求把每个英文词都翻译成中文，也不把普通操作和整段说明保留为英文。

- 不翻译的术语、固定译法和大小写统一维护在本文件的“术语约定”中。
- 优先保证整句自然易懂。上下文明确时省略重复的概念名称，不为体现产品术语而刻意堆叠英文。
- 按钮使用明确的动作，例如“新建”“保存”“重命名”“归档”。
- 空状态说明当前情况；必要时给出下一步，不堆叠技术细节。
- 错误说明发生了什么，以及用户能做什么；保留原有事实和限制。
- 确认文案明确对象及后果；不可逆、数据删除等信息不得在翻译中遗漏。
- 中文使用中文句式和标点，避免英文语序直译；英文使用自然语法。
- 保持动作语义区别，例如归档与删除、关闭与停止、打开与恢复，不为统一措辞而改变含义。

| 英文界面 | 中文界面 |
| --- | --- |
| New Project | 新建 Project |
| Rename Workspace | 重命名 Workspace |
| Archive Session | 归档 Session |
| Agent Integration | Agent 集成 |
| No Workspaces yet | 暂无 Workspace |
| Delete this Session permanently? | 确定永久删除这个 Session？ |

这些示例展示文风，不代表每个对象都提供相应操作。

## 术语约定

本节是术语决定的唯一维护入口。以下词在中文界面也保留英文，不附加中文括注；TOML 列表保存最终展示的标准拼写。

```toml
preserve = [
  "Treefold", "Codex", "Git", "amux", "Workspace", "Fork", "Project", "Session", "Agent", "Skill",
  "AI", "API", "CLI", "SDK", "MCP", "Todo", "Context", "feature",
]
```

- **识别时忽略大小写，展示时遵循标准拼写。** 例如 `workspace`、`Workspace`、`WORKSPACE` 表示同一产品概念时，统一展示为 `Workspace`；`Git` 保留首字母大写，`amux` 保持小写。无需列出大小写变体。
- 产品层级：Project 组织项目，Workspace 承担一项独立的 feature，Fork 承担该 feature 的子任务。`feature` 保持小写；不要将 Fork 的主要用途描述为尝试另一种方案，也不要将 Project Session 作为常规开发起点。
- 技术缩写 AI、API、CLI、SDK、MCP 统一大写；Todo 和 Context 作为产品功能或技术概念时保留英文，普通描述按语境处理。
- 按概念和语境判断，不做全文机械替换。Workspace 不译为“工作区”或“工作流”，Fork 不译为“分叉”或“分支”，Project、Session、Agent、Skill 分别保留英文，不译为“项目”“会话”“智能体”“技能”。普通描述中的同形词按语境处理，例如 Git branch 仍可译为“分支”。
- 中文句子中的概念词用单数形式，如“3 个 Session”“管理 Skill”；英文界面按语法使用 Projects、Sessions、Skills 等复数。
- 中文与英文或数字之间留一个空格，如“新建 Project”“共 3 个 Session”。标点旁不额外加空格。
- 用户输入、文件路径、命令、参数、配置键、代码及 API 标识符保持原值，不应用展示大小写规则；例如命令中的 `git` 不改成 `Git`。
- Git History 的提交右键菜单使用英文 Git 动作风格，并在中英文界面保持一致：`View Diff`、`Copy Commit`、`Revert Commit`、`Reset to Commit`、`Squash Commits…`。确认对话框中的说明、状态和操作后果继续使用界面语言。
- 新增产品名遵循其官方拼写。新增核心概念或固定中文译法时，先在本节记录选定写法、含义和使用边界，再更新语言包；存在歧义时确认具体概念，不从旧文案推断全局规则。

## 文件职责

| 文件 | 职责 |
| --- | --- |
| `AGENTS.md` | 术语约定、文案偏好、翻译步骤和检查要求 |
| `locales/en-US.ts` | 英文文案及 `LocaleMessages` 结构定义 |
| `locales/zh-CN.ts` | 中文文案，通过 `satisfies LocaleMessages` 对齐结构 |
| `index.ts` | i18next 初始化和语言选择 |

术语表用于创作和审查，不做运行时字符串替换。语言包保留完整句子，避免用术语和句子片段拼接导致语序或空格错误。

## 每次翻译的执行步骤

1. **读取规范并确定范围。** 先读本文件及其中的术语约定，定位目标功能及对应语言包 key。检查实际调用位置，理解对象、状态、操作后果与插值来源。
2. **检查覆盖。** 在目标范围内检查可见文本、菜单、对话框、占位提示、tooltip、通知、空状态、错误和可访问名称，识别遗漏的硬编码文案。用户内容及原始命令输出不作为待翻译文案。
3. **确定术语。** 应用本文件的术语约定；新增术语决定先更新本文件的“术语约定”。旧文案若不符合规范，不将其作为译法依据。只修改本次范围内的文案，其余问题在交付中列明。
4. **更新两种语言。** 通过现有 i18next 机制使用完整文案；保持 key 的功能归属，不因展示词变化重命名稳定 key。新增、删除 key 时同步两份语言包。
5. **逐项对照。** 保留 `{{name}}`、`{{count}}` 等插值名称及所需变量，允许按语序调整位置。检查复数、数量、换行、标点、英文大小写及中英文间距。确认两种语言表达相同的条件、动作和后果。
6. **验证并交付。** 按下面的范围要求验证，说明修改的功能、术语决定、执行的检查，以及仍有的遗漏或验证边界。

不要翻译用户创建的名称、路径、命令、参数和配置键。对后端提供的文本先确认来源与接口契约，不通过模糊匹配英文错误消息来实现翻译。

## 检查要求

- 纯规范文档变更：审查 diff 并运行 `git diff --check`。
- 语言包或 React 文案变更：审查两种语言的 diff，运行 `git diff --check` 和 `just typecheck`。类型对齐不能证明插值或语义正确，仍需逐项审查。
- 纯文案变更不新增永久 UI 测试，不默认启动 Electron 或截图。
- 如果改动影响可访问名称、键盘行为或其他行为契约，检查相关消费者并运行最小的现有测试用例。只有满足仓库 UI-test admission gate 时才新增或修改测试。
- 长文案造成截断、溢出、遮挡等具体风险时，按根目录 `AGENTS.md` 的视觉验证要求进行隐藏 Electron 诊断；未经用户要求，不进行手动桌面验收。
- 批次验证和扩大检查范围遵循根目录 `AGENTS.md`；不因翻译工作默认运行完整构建或全量测试。

## 交付前核对

- [ ] 术语符合本文件的术语约定，没有同一概念的多种写法。
- [ ] 中文操作和说明自然易懂，英文语法及单复数正确。
- [ ] 两种语言的 key、插值和语义一致，未改变业务行为。
- [ ] 本次范围内的文案入口已检查，用户内容与技术标识符保持原值。
- [ ] 已完成适用检查，并明确剩余问题或验证边界。
